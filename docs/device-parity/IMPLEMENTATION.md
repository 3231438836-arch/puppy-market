# v0.5.1 电脑/手机一致性审计与修复

## 审计结论与真实部署限制

本次开始时工作区干净，源码开发分支为4bb6b19（v0.5.0），main仍为ce90da4，gh-pages仍为ac9b234。没有自动发布任何站点。用户提供了GitHub Pages与Cloudflare Workers两个不同入口：

- https://3231438836-arch.github.io/puppy-market/?v=3
- https://puppy-market.3231438836.workers.dev/

本次再次请求两者首页和version.json，均被当前执行环境的代理以403拒绝。见 [原始访问结果](live-access-observations.json)。这不证明网站对玩家不可访问，也无法据此断言两台设备实际加载了相同或不同的版本，不能猜测Cloudflare的部署分支/时间/SHA。

比较完整URL（域名、路径和mode/preview/training/npc-preview等模式）、游戏设置中的构建信息及存档槽。`?v=3`不选择Git分支。Git发布分支的历史来源与线上服务端当前实际状态必须分开。

## 逐项差异清单

| 检查项 | 证据 / 位置 | 结论与处理 |
|---|---|---|
| 电脑/手机部署版本 | 版本由vite.config.ts编译注入，外网访问受限 | 实际两端版本无法远程确认；保留版本/日期/SHA，增加只读检查和进度/槽位信息 |
| PWA/Service Worker | main.ts、index.html及源码搜索无注册SW、无manifest/PWA安装流程 | 没有证据说项目SW导致手机旧缓存；不能检查用户另一浏览器的注册。诊断按钮读取当前注册数与控制状态，不注销 |
| CSS按屏幕删除功能 | layout.css / immersive.css / experience.css | 未找到手机专属删玩法；横屏仅在进入游戏前隐藏地图，实际游戏共用模拟。面板/相机视野随尺寸变化 |
| 明日预告初始可见性 | growth-ui.ts原先只在结算底部输出level-card | 同一状态实测桌面1280×900可见，390×844竖屏可见；844×390横屏和320×568窄屏位于结算可视区外。没有独立入口，发现成本不同 |
| 明日预告数据 | business.ts的nextLevel、data/business.json的levels | 原数据非随机；本轮抽出tomorrow.ts供结算与独立预告共用，不添加未来NPC或未经配置功能 |
| 闭店HUD菜单 | app.ts原渲染先判断closed，且dialog遮罩位于HUD之上 | 原HUD任务在结算阶段既可能被覆盖又无法直接点到。修复显式面板优先级，并在结算/目录/布置标题栏内增加可点“菜单”入口，不让背景按钮穿透遮罩 |
| 320px设置触摸无响应 | scene.ts货架标签pointerdown；device-parity.spec.ts触摸事件审计 | 真实复现pointerdown目标是settings，后续pointerup/click却变成库存dismiss；Phaser背后缺货标签抢先处理触摸。过滤来自controls/layout-modal的场景点击后四尺寸均通过 |
| Hover依赖 | 源码搜索mouseover/mouseenter/:hover以及实际点击 | 未发现关键玩法仅靠hover开放；旧title属性为辅助说明。新菜单直接写出“打烊后开放”“今晚已结束”等可读状态 |
| 日记/手册/图鉴入口 | app.ts、manual.ts、guest-book-ui.ts、diary.ts | 文学手册须先在宿舍发现；日记只生成于睡觉后；图鉴未知状态隐藏身份。共用菜单提供已解锁读物/历史/图鉴入口，不因手机减少功能，也不提前解锁 |
| 家具入口 | furniture-ui.ts、app.ts | 日间明确标“打烊后开放”；结算标题菜单可进入目录与布置。第一夜购物已结束后保留回宿舍流程，不可借菜单绕过 |
| 宿舍 | world.ts fixtures、scene.ts、app.ts | 菜单提供真实楼梯方向箭头，不瞬移。仍需WASD/摇杆走到同一入口，E或触摸进入，原入口返回 |
| 存档是否相同 | app.ts sessionKey选择、persistence.ts | 同一浏览器/同一域名/同一模式共用相同键；不同设备、浏览器、域名和独立预览槽本来独立。本轮不引入云同步，不迁移/清空/替换这些数据 |

[修复前四尺寸观察](baseline-observations.json) 和audit截图为修改前实测，保持不覆盖。[修复后布局观察](layout-observations.json) 由回归测试生成。宽屏能看到更多地图范围属于相机视野差异，不意味着解锁了手机没有的规则。

## 用户可见改动

1. 营业时按HUD“任务”打开经营与游戏菜单，直接进入明日预告、来客簿、已发现手册、历史日记、宿舍方向、夜间购物及家具仓库。各入口按真实状态显示开放条件。
2. 结算、目录、布置的固定标题栏有“菜单”按钮；独立面板关闭后回到原夜间阶段，不重新结算、不跳天、不重新抽目录。
3. 设置也可进入明日预告。预告依据实际等级/XP/已开放商品；明确“达到等级后解锁，是否明天取决于经营经验”，不承诺第二天自动获得，不显示未遇角色。
4. 文学手册仍遵守第一夜发现条件；新菜单不是提前把它放进背包。日记入口只读已完成文本，不生成新日记。
5. 设置保留版本、日期、提交；增加当前游戏日、Level、地点和存档槽，帮助区分设备上的不同进度。
6. “检查当前版本（保留存档）”以no-store请求同源版本清单，读取Service Worker注册数/是否控制当前页；不清空localStorage、不注销SW、不删除CacheStorage。清单一致只证明页面与清单匹配，不代表已经读取平台后台部署记录。

## 第一日日记定稿接入

用户本轮补充的第一天定稿已原文写入 `src/data/diaries.json`，状态approved。仅在manualFound=true时加入“在床上发现《员工须知》”与“看起来已经被翻过很多次了”两句；未发现则省略两句，保留其余全部定稿，不另写替代故事。后一句不要求读完，manualRead=false也可出现。

家具购买与特殊顾客条件继续记录到context，但不自动添写额外文学内容。正式生成时保存日期、实际文本和条件结果；同一日不重抽、不改写，合上前退出可恢复，合上后进入次日。

旧版已保存的空白占位日记不被新定稿覆盖，读取时如实说明“旧版本未记录”，而不是继续说作者尚未提供正文。其他日期未扩写。若旧测试槽已经过第一晚，可使用独立新档入口首次测试或无痕窗口，不用清空原经营存档。
